# Lab 2: From event to detection

**SDLC phase:** Operate · **Stage:** Agent Augmented · **Time:** 40 minutes

## Why this matters

Claude Code sends the raw events. Detection, correlation and alerting are your job, in your SIEM. In this lab you replay a prompt-injection story, catch it with starter detections, and rebuild what happened from one `prompt_id`, the way you would in an incident.

## Before you start

This lab needs nothing beyond the workshop repository, and the LGTM container from Lab 1.

- Open a terminal in your `my-claude-code-observability-secops` folder.
- Open `secops/detections.md` in your editor. Every query in this lab comes from it.
- If you stopped the container after Lab 1, start it again with `./scripts/run-lgtm.sh`.

## Steps

### Step 1: Look at the story before you send it

**Do this.** Print the synthetic events without sending them.

```bash
python3 secops/seed-suspicious-events.py --dry-run
```

What this does: prints 12 made-up events for `mallory@example.com`, one per line, and sends nothing. It changes nothing.

**What you should see.** Twelve lines of JSON. Three come before any prompt: a switch to `bypassPermissions`, an unofficial plugin and an MCP server. The other nine share one `prompt.id`.

**Why.** Every value is synthetic. Nobody runs a risky command, so you can practise on a real attack shape safely.

### Step 2: Send the story to the stack

**Do this.** Send the events to the Collector.

```bash
python3 secops/seed-suspicious-events.py
```

What this does: sends the 12 events to `http://localhost:4318/v1/logs`, the same OTLP endpoint Claude Code uses, and prints the `session_id` and `prompt_id` it used. It changes no files.

**What you should see.** `Sent 12 events for mallory@example.com.` and two IDs.

**Why.** To Loki these look like Claude Code's own events, so the detections you write against them work on real ones.

### Step 3: Run detections D1 to D6

**Do this.** In Grafana, open **Explore**, choose **Loki**, switch to **Code**, and set the time range to **Last 1 hour**. Read the one-line explanation of each detection in `secops/detections.md`, then paste its query into the query box and press **Run query**. Do D1 to D6 in order. This is D1:

```logql
{service_name="claude-code"} | event_name="permission_mode_changed" | to_mode="bypassPermissions"
```

**What you should see.** Each of D1 to D6 returns one line for `mallory@example.com`: the bypass switch, the `curl` upload blocked by a hook, the `.env` read, the `notes-sync` MCP server, the unofficial plugin and the hook that blocked. Ignore any lines from your own sessions, such as your own MCP servers or plugins.

**Why.** A detection is only a filter on fields. Without `OTEL_LOG_TOOL_DETAILS=1`, D2 and D3 have nothing to match on, and D4 matches every MCP connection.

### Step 4: Pivot on the prompt

**Do this.** Open D2's result line and copy its `prompt_id`. Paste this query into the query box, put the `prompt_id` in place of `PASTE-PROMPT-ID-HERE`, and press **Run query**:

```logql
{service_name="claude-code"} | prompt_id="PASTE-PROMPT-ID-HERE"
```

Sort the results oldest first with the sort-order setting above the log lines, and read the `event_sequence` field on each line.

**What you should see.** Nine events, `event_sequence` 3 to 11. In order: the `user_prompt`; a `tool_decision` and a `tool_result` for reading `README.md`, then the same pair for `.env`; a `hook_execution_complete` with one blocking hook; the rejected `curl` decision; then a `WebFetch` decision and result, both accepted, to the same `paste.example.net` host.

**Why.** `prompt_id` ties together everything one instruction caused. One query gives you the whole story, including what the agent read before it acted.

### Step 5: Catch the reroute

**Do this.** Run D7, the two-step hunt in `secops/detections.md`. Paste the second query into the query box and press **Run query**:

```logql
{service_name="claude-code"} | event_name=~"tool_decision|tool_result" | tool_parameters=~`.*paste\.example\.net.*`
```

**What you should see.** Three lines: the rejected `Bash` decision, then a `WebFetch` decision and its `tool_result`, both accepted.

**Why.** An agent that is blocked one way and reaches the same host another way is behaving like an attacker, whether or not a person meant it to.

### Step 6: See the trace and the cost of your own session

**Do this.** Your Lab 1 session also sent traces and metrics. In **Explore**, choose **Tempo**, then the **Search** tab, set **Service Name** to `claude-code`, and press **Run query**. Open one trace. Then choose **Prometheus**, switch to **Code**, paste this query into the query box and press **Run query**:

```promql
sum by (type) (claude_code_token_usage_tokens_total)
```

**What you should see.** In Tempo, a `claude_code.interaction` span for each prompt, with `claude_code.llm_request` and `claude_code.tool` spans under it. In Prometheus, token counts by type, such as `input` and `output`.

**Why.** The trace shows causality inside one prompt. Metrics give you the baselines that make a spike visible.

### Step 7: Turn D1 into an alert rule

**Do this.** Send the story once more, so the alert has fresh events to count.

```bash
python3 secops/seed-suspicious-events.py
```

What this does: sends the 12 synthetic events again, with new IDs. It changes no files.

In Grafana, open **Alerting**, then **Alert rules**, then **New alert rule**. Choose **Loki** as the data source and paste this query into the query box:

```logql
sum by (user_email) (count_over_time({service_name="claude-code"} | event_name="permission_mode_changed" | to_mode="bypassPermissions" [5m]))
```

Run the query in the rule form, then set the threshold to **Is above 0**. Give the rule a name such as `D1 bypass mode`. Grafana also asks for a folder and an evaluation group: create a folder named `workshop` and a group named `detections` with an interval of `1m`. Save the rule.

**What you should see.** The rule's preview shows one series for `mallory@example.com` with the value 1. The value is higher if your first run of the seeder is still inside the last five minutes. The saved rule appears in the list.

**Why.** An alert needs a number. `count_over_time` turns matching lines into one, per user.

## You're done when

Your `prompt_id` query in step 4 returns nine events in order. Post the number of events in the chat.

## If it goes wrong

- **`Could not reach http://localhost:4318/v1/logs`:** the LGTM container is not running. Start it with `./scripts/run-lgtm.sh`, then run step 2 again.
- **A detection returns nothing:** check the time range is **Last 1 hour**, and that you ran step 2 in the last hour. If you ran step 2 twice, each run has its own `prompt_id`, so the pivot still returns nine.
- **The alert preview shows no data:** the query counts the last five minutes. Run the seeder again, then refresh the preview.
- **`parse error` in Loki:** you pasted part of a query. Copy the whole block again.
- **Tempo or Prometheus shows nothing:** your Lab 1 session ran before the traces and metrics settings were sourced, or more than an hour ago. Run step 2 of Lab 1 again, then start Claude Code and send one prompt as in step 5 of Lab 1, then retry.

## Stretch goals

- Write a D8 of your own in `secops/detections.md`, for example an MCP server that failed to connect. Test it on the seeded events.
- Put the Collector to work as a security control. Stop the stack with `./scripts/stop-lgtm.sh`, then start it with the SecOps config:

  ```bash
  ./scripts/run-lgtm.sh --collector secops/otel-collector-secops.yaml
  ```

  What this does: starts the stack with `secops/otel-collector-secops.yaml` as the Collector's config. It redacts secrets, and sends only security events to a stand-in SIEM, the Collector's own output. It changes no files.

  Send events that carry fake secrets:

  ```bash
  python3 secops/seed-suspicious-events.py --secret-test
  ```

  What this does: sends a Bash event with a fake AWS key and bearer token in it, and one `api_request` event. It changes no files.

  In Loki, the command shows `[REDACTED:aws_key]` and `[REDACTED:token]`. In `docker logs workshop-lgtm`, the stand-in SIEM, only the Bash event appears.

You replayed a prompt-injection story, caught it with seven detections, rebuilt it from one `prompt_id`, and turned a detection into an alert. In Lab 3 you add a control point that every model request has to pass through.
